整理日期：2026-11-01。调研围绕现有 Demo 的选型、实现与后续验证展开。

## 1. 技术选择

| 问题 | 当前选择与依据 | 后续评估方向 |
| --- | --- | --- |
| 阅读界面与业务接口 | 复用 Papernook 的 Next.js/React、PDF 阅读器、文件保存和研究接口，在同一应用中承接交互与本机文件操作。 | 根据试用发现优化入口与状态反馈。 |
| PDF 阅读与批注 | PDF.js 解析和呈现 PDF，结合现有保存流程将标记写入 PDF；沿用可移植的文件成果。[PDF.js 官方说明](https://mozilla.github.io/pdf.js/) | 扫描件识别、复杂版面与跨设备标记兼容性。 |
| 个人全文检索 | better-sqlite3 与 SQLite FTS5，利用已有全文索引和 BM25 排序；文件保留为真源，索引可重建。[FTS5 官方说明](https://www.sqlite.org/fts5.html) | 用中文查询集评估召回，再比较专用分词、trigram 或语义检索。 |
| 图谱呈现 | Cytoscape.js 与 fCoSE，支持节点、边、筛选和图像导出；关系数据直接保存在工作区文件。[Cytoscape.js 官方说明](https://js.cytoscape.org/) | 大图布局耗时及证据面板的可读性。 |
| 模型任务 | 复用 PaperFlow AgentRunner、工具权限、事件和会话存储，研究服务自带 TCP RPC；端点和密钥由私有配置提供。 | 为不同 OpenAI 兼容端点评估输出结构、时延和调用成本。 |
| 部署与保存 | 根目录 Docker Compose 运行 Web 和 Python 两个服务，使用本机文件和 SQLite，无需外部数据库服务器。 | 在干净环境验证配置、升级、备份和恢复。 |

上述选择优先复用现有阅读和存储能力。当前实现不依赖向量数据库、浏览器 WASM 图数据库或额外 embedding 服务；后续引入新组件需先验证其对实际任务的收益。

## 2. FTS5、BM25 与中文补充检索

### 2.1 索引与分块

[index-db.ts](../../app/src/lib/library/index-db.ts)建立 `papers_fts` 与 `chunks_fts`。论文索引覆盖标题、作者、标签、摘要和正文；正文尽量按段落合并，目标块长约 1200 字符，过长段落继续切分，并保留字符起点。

论文检索转义查询词并使用前缀匹配；段落检索使用 OR 连接词项，在指定论文内取匹配块。两者通过 `ORDER BY rank` 排序；该 FTS5 隐藏列默认采用 BM25。这里复用 SQLite 的算法，没有另行训练或手写 BM25。[FTS5 排序说明](https://www.sqlite.org/fts5.html#sorting_by_auxiliary_function_results)

### 2.2 Web 端中文补充与合并

[store.ts](../../app/src/lib/research/store.ts)中的 `searchResearch`先尝试 FTS，再检查可见论文、逐页正文、已确认笔记、批注和概念条目。

1. 查询与文本做小写和 NFKC 规范化；完整字面命中计 `30 + 查询长度`。
2. 否则提取英文数字词与连续中文词，命中词项按长度计分、单项最多 15 分；中文词未整体命中时，检查相邻二字片段并累加。
3. FTS 论文结果按 `100 - 名次`、块定位到页面的结果按 `90 - 名次`加入候选，再与本地启发式结果合并。
4. 按最终分数排序，对结果 ID 去重，最多返回 100 项。

因此最终展示分数是多路规则的合并排序值，并非统一的 BM25 分数。中文补充能覆盖部分连续中文词漏检，但二字片段可能带来噪声；检索质量需用真实问题与相关页标注评估。

### 2.3 Python 工具检索

[research_context.py](../../services/research_context.py)的 `search_paper`仅遍历本轮传入的来源页。它对完整查询、英文关键词、较短中文词和较长中文词的二字片段进行匹配，以词长、命中次数和完整查询加权，返回真实页码、片段和回跳链接；默认 4 条、最多 6 条。

该工具是受限资料池内的逐页启发式检索，与 SQLite BM25 是两个独立实现。它使 AgentRunner 能继续查找当前材料的后续页面，同时维持用户选择的来源边界。

## 3. 带证据的图谱

[graph.ts](../../app/src/lib/research/graph.ts)保存论文、概念、已确认笔记及其关系。

| 步骤 | 当前实现 |
| --- | --- |
| 本地匹配 | 按概念标题及别名查找逐页正文，为“涉及概念”生成最多 3 条页级证据；两篇论文共同出现同一概念时生成共同主题候选。 |
| 显式 AI 提取 | 用户发起 PaperFlow 任务；结构化结果限定概念、释义、页码、摘录及 `discusses`、`uses_method`、`reports` 关系。 |
| 来源校验 | 以 NFKC、去空白和小写规范化后，检查摘录是否存在于指定页；正文版本不匹配的任务不直接应用。 |
| 去重与人工判断 | 节点和边使用规范化内容的摘要标识；重复提取复用已有记录并保留确认或拒绝状态；同一次任务只应用一次。 |
| 来源更新 | 边携带论文、页码、摘录和正文版本；原文或共同概念证据改变后标记待重新定位。 |

关系中的“共同涉及概念”表达共同主题。摘录校验能阻止不存在的引用入库，不能自动证明关系解释正确，最终语义由读者核对。

## 4. 模型任务与调用成本

[research_service.py](../../services/research_service.py)复用 [AgentRunner](../../services/paperflow/src/paperflow/core/runner.py)，通过研究专用工具读取本轮材料、提出草稿并等待相关确认；[transport.ts](../../app/src/lib/paperflow/transport.ts)用换行分帧的 JSON 传递 RPC。

导入、索引、中文检索、本地概念匹配及批注整理采用本机确定性逻辑；解释、分析、出题与显式 AI 提取才调用用户配置的模型。单次整篇分析上下文最多装入 10 万字符，界面提示截断范围，工具可在所选来源内继续按页读取。
