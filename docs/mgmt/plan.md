# 项目计划与角色分工

整理日期：2026-11-02。项目已有完整 Demo，本计划用于发布整理、验证与首轮迭代。下列周次为后续安排，不代表已经发生的开发历史。

当前发布归入 [v0.1 本机可复现部署里程碑](https://github.com/Muhaymenul/openhai/milestone/1)，安装、源码交付及首轮检查在 [Issue #6](https://github.com/Muhaymenul/openhai/issues/6) 跟踪。任务状态维护在[仓库看板](kanban.md)，缺陷通过 [Issues](https://github.com/Muhaymenul/openhai/issues) 登记。

## 1. 角色与责任

| 角色 | 主要责任 | 认领状态 |
| --- | --- | --- |
| 产品与需求 | 确认目标读者、维护用户故事、组织首轮试用及反馈排序。 | 待认领 |
| 交互与前端 | 阅读、笔记、复习与图谱交互，状态提示和浏览器体验。 | 待认领 |
| 服务与算法 | 文件保存、检索、证据校验、PaperFlow 集成及 API 配置。 | 待认领 |
| 测试与质量 | 回归测试、干净安装、异常恢复、来源范围和导出检查。 | 待认领 |
| 发布与文档 | README、部署配置、许可、持续集成与交付清单。 | 待认领 |

同一人可承担多个角色，认领后在[看板](kanban.md)登记负责人。当前不填写未经确认的成员姓名。

## 3. 里程碑

| 阶段 | 计划窗口 | 主要任务 | 交付与完成条件 |
| --- | --- | --- | --- |
| M1 分析 | 发布整理第 1 周 | 根据已有 Demo 收敛问题定义、功能范围、用户故事与试用假设。 | 四份需求文档相互对应，明确首轮 3–5 人试用是计划。 |
| M2 设计 | 第 1 周 | 明确逻辑分层、文件数据模型、资料范围和检索/图谱机制。 | 架构图和技术调研可对应真实源码，运行目录保持一致。 |
| M3 开发整理 | 第 1–2 周 | 完成通用配置、发布目录和发现的问题修复，保留许可证。 | 干净源码不含私有数据、模型密钥和本机专用路径；部署说明一致。 |
| M4 测试 | 第 2 周 | 执行核心回归、无 AI 全流程、配置后的 AI 验收、导出与恢复演练。 | 记录环境、命令、结果和待修问题，关键保存与来源问题关闭。 |
| M5 发布 | 第 2 周 | 完成安装说明、CI、交付清单与演示流程，整理发布候选。 | 新环境能够照说明运行；形成可检查的交付内容。公开发布状态以实际操作为准。 |
| M6 迭代 | 第 3 周起 | 招募 3–5 人试用，整理任务完成记录；建立中文检索查询集。 | 得到实际反馈及优先级，确定下一轮具体改进与验收项。 |

## 4. 工作节奏与验收

每周维护看板，明确本周目标、负责人、验证证据与未解决问题。每个任务完成时更新文档或代码入口，并附可复现的检查方法；把代码已存在、测试已执行和用户已验证分开记录。

发布前以[用户故事](../requirements/user_stories.md)组织演示，以[非功能规格](../requirements/nonfunctional_spec.md)检查数据、来源和恢复。真实模型验收由明确配置的使用者额度承担，与无模型测试分开安排。

## 5. 依赖与调整

| 依赖或风险 | 对计划的影响 | 处理安排 |
| --- | --- | --- |
| Docker 与基础镜像获取 | 影响首次安装和新环境复现。 | 提前进行干净构建，记录网络和版本条件。 |
| API 端点、模型与额度 | 影响解释、分析和出题验证。 | 先完成无 AI 验收，再用自己的配置执行小范围真实调用。 |
| 中文检索缺少标注集 | 暂时不能用量化结论比较检索方案。 | 迭代阶段建立查询—相关页集合，再评估分词或语义检索。 |
| 首轮试用尚未开展 | 易用性与学习效果假设仍待验证。 | 使用统一任务记录行为与问题，不以功能数量代替用户验证。 |
| 团队角色待认领 | 任务责任和并行安排尚未确定。 | 首次协作时认领角色，再确认各里程碑日期。 |
